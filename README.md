# How much is an FMA-small accuracy worth if nobody states the split?

Accuracy on FMA-small depends on a choice almost no paper discloses: whether the train/test
boundary falls between artists, between tracks, or between 3-second clips of the same
recording. We train every architecture in this repository down all three rungs of that
ladder under otherwise identical conditions, and the same model moves by tens of accuracy
points from one rung to the next. We then report our own best result under the strictest
rung — FMA's official artist-filtered split, scored per track — and make no claim about
where anyone else's number belongs, because the papers do not say.

**This repository indicts a reporting convention, not an author.** Of the nine published
FMA-small results we traced to a primary source, none states in prose that it used the
artist-filtered split; most give a ratio without naming the unit it applies to. That makes
their numbers *unplaceable*, not *inflated*. We never infer a protocol from an accuracy —
doing so would assume the very conclusion this project is trying to measure.

## The two rules everything here obeys

**Track-level, always.** We train on 3-second episodes but a *track* is the thing being
classified, so per-episode probabilities are averaged within a track before the argmax.
Episode-level accuracy runs several points lower and is never reported beside a published
figure — pairing the two once produced a confident false conclusion in this project, kept
visible in `docs/NEGATIVE_RESULTS.md` §4 rather than quietly corrected. The generators read
`eval_metrics.json → track_level` and never `summary.json`.

**Artist-filtered, for anything called a result.** The `random_track` and `random_clip` runs
exist to measure the cost of leaking; they are diagnostic instruments and appear only in the
ladder and the experiment log, labelled as such. No run with a non-official split may enter
the headline table, and `scripts/update_results.py` enforces that rather than trusting us to
remember it.

## Reproduction

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

```bash
# Data
python -m src.data.download_fma
python -m src.data.process_fma

# Backbone features, cached once (probes then train in minutes and touch no audio)
python -m src.data.extract_embeddings --workers 4              # MERT-v1-95M, ~2h
python -m src.data.extract_mert_large_embeddings --workers 4   # MERT-v1-330M, ~3.5h

# One config per run, one entrypoint
python -m src.training.train --config src/training/configs/mert_flat_probe_v1.yaml
python -m src.evaluation.metrics --run mert_flat_probe_v1
python -m src.evaluation.cache_outputs --run mert_flat_probe_v1   # for ensembling

# The ladder: same config, three splits
bash scripts/run_ladder_queue.sh          # strictly sequential — see Hardware
python scripts/protocol_leakage_analysis.py

# Regenerate the results documents
python scripts/update_results.py
```

A config names the model, its hyperparameters, the seed, and — for the leaky rungs — a
`split_mode` of `random_track` or `random_clip`. Absent that key, a run is artist-filtered.

## Layout

```
src/
  data/           Download, validate, preprocess FMA-small; extract backbone embeddings
  models/         GenreCNN, MERT probes (weighted-sum / flat / deep / attention),
                  EmbeddingProbe (BYOL-A, PANNs), and reimplementations:
                  GenreDenseNet, DualCNN, CNNBiGRU, CapsNet, CNNTransformer
  training/       Config-driven train.py, dataset classes with the three split modes
  evaluation/     Track-level metrics, output caching, baseline comparison
  config.py       Shared paths and constants
scripts/          The ladder, the generators, ensembling, analysis utilities
dgx-code/         DGX fine-tuning pipeline (LoRA, AST, HTS-AT, EfficientAT, ensembles)
docs/             See the tables above
docs/form-submission/  Standalone LaTeX — compiles with `make pdf`, no pandoc needed
```

## Hardware

**Laptop (probes + from-scratch models):** Apple M-series chip (MPS backend). Spectrogram
models take 30–60 minutes per run; probes over cached embeddings take 1–3 minutes. Embedding
extraction wants ~16 GB of RAM. **Runs must be sequential** — two jobs contending for the
single MPS device took DenseNet from 350s/epoch to 1800s/epoch.

**DGX (fine-tuning + large probes):** NVIDIA H200 single-GPU. Round 1 fine-tuning (~6
GPU-hours) and Round 2 frozen-encoder probes + ensembles. Best single model: AST Probe
62.0%; best ensemble: 62.1%.
